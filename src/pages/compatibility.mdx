# Совместимость пакетов Triangle

Эта страница фиксирует **снимок объявленных зависимостей в checkout от 1 ноября 2026 года**. Это не обещание совместимости релизов: фактическую совместимость подтверждают только согласованные lock-файлы, установка и тесты совместно работающих пакетов.

## Что сейчас подтверждено

- Текущая линия выполнения Triangle состоит из HTTP `Web` и realtime `WS` tracks. `Full` — шаблон административной панели, `Maestro` — прототип управления несколькими приложениями; это отдельные продуктовые направления, а не дополнительные execution tracks.
- Server — нижележащий асинхронный runtime. Его PHP API нельзя смешивать с версиями пакетов Triangle.
- Locks основных компонентов, HTTP/WS движков и Web/WS сборок пересозданы из текущих manifests. Это подтверждает разрешимость зависимостей, но не совместимость поведения на runtime.
- Локальные vendor-директории в NTFS/FUSE checkout не используются для проверки; пакеты ставились во временные каталоги. Для `Plugin-Media` и legacy плагинов установка/runtime не подтверждены.
- Прямое использование библиотек вне Triangle — цель совместимости, но не каждый текущий пакет независим от Engine: например, Router и Middleware объявляют Engine в `require`. Для standalone use необходимо отдельно определить минимальные контракты и адаптеры.
- `Maestro` задуман как управляющая среда для нескольких приложений на Triangle/Localzet Server. В проверенной реализации есть несколько listener-конфигураций и монитор файлов/памяти; reverse proxy, upstream routing, health checks, независимая перезагрузка и resource isolation этим checkout не подтверждены. Смотрите отдельный README Maestro.
- `Full` содержит frontend-шаблон административной панели и базовый Triangle application example. Наличие экранов интерфейса не означает готовые CRUD, аутентификацию, роли или backend панели. Пакетный identity пока совпадает с `triangle/web`.
- `Metronic` — архивная сборка старого поколения и не входит в поддерживаемую матрицу.
- Манифесты `triangle/engine-http` и `triangle/engine-ws` явно объявляют взаимный Composer `conflict: "*"`; их нельзя установить вместе в один Composer dependency graph. Это закрепляет отдельные application tracks на уровне пакетов. Вопрос об использовании отдельных приложений/процессов на одном Localzet Server deployment — отдельная эксплуатационная архитектура.

## Границы поколений

Не смешивайте `Engine 5/6/7/8`, `Router/Middleware 1/2` и Web/WS templates по совпадению namespace. До стабилизации release train используйте lock-файл конкретного приложения и проверяйте, что его прямые и транзитивные зависимости удовлетворяют всем constraints.

Матрица остаётся снимком Composer-контрактов, пока не пройдены интеграционные проверки `Server → Engine → HTTP/WS Engine → framework`. `Pusher` остаётся незавершённым прототипом. OAuth декларирует Triangle Engine, но совместимость интеграции требует runtime-проверки.

## Предложение по идентификаторам проектов

Несколько независимых project checkouts сейчас объявляют `name: triangle/web`. Это не меняет runtime API, но затрудняет навигацию, отчёты зависимостей, Packagist metadata и понимание lock-файлов. Для root-проектов предлагается такая схема:

| Checkout | Текущий Composer name | Предлагаемый name | Роль |
| --- | --- | --- | --- |
| `Web` | `triangle/web` | `triangle/web` | Канонический HTTP application template |
| `Web-Managed` | `triangle/web` | `triangle/web-managed` | Вариант Web с управляемой конфигурацией |
| `Full` | `triangle/web` | `triangle/full` | Панель административного интерфейса для Triangle-приложений |
| `Maestro` | `triangle/maestro` | — | Управляющая среда для нескольких приложений; прототип |
| `Ws` | `triangle/ws` | `triangle/ws` | WebSocket application template |
| `Metronic` | `triangle/web` | без переименования в рамках актуального train | Архив; оставить исторические метаданные |

Предложение касается только поля `name` корневых проектов `type: project`; зависимости приложений от `triangle/engine`, `triangle/engine-http` и компонентов не меняются. Перед применением к публичным репозиториям нужно проверить существующие Packagist публикации и теги, downstream-команды `composer create-project`, release automation и документационные ссылки. Если checkout используются только как шаблоны в GitHub, package name должен соответствовать фактическому способу установки, а не создавать фиктивный публикуемый пакет.
